# Game 2048 Design Specification

Date: 2026-09-17  
Status: Approved for implementation planning

## Objective

Add a production-quality 2048 game to Kita Story. The game must follow the existing feature-first architecture and soft pastel visual language, support smooth tile movement and merge animations, persist an active run locally, record completed runs in Supabase, provide a couple leaderboard, and award abuse-resistant application points for one-time tile milestones.

## Scope

The first version includes:

- a 4x4 standard 2048 board;
- endless play after the first 2048 tile;
- three undo actions per run;
- local autosave and resume;
- standard 2048 score and best score;
- one-time application-point milestones;
- game history, couple leaderboard, and recent-run history;
- animated tile movement, spawn, merge, and score changes;
- 2048 celebration and game-over overlays;
- confirmation flows for leaving or replacing an active run;
- integration from the existing Games screen.

The first version excludes multiplayer turns, cloud synchronization of an in-progress board, paid/replenishable undo, alternative board sizes, power-ups, and online global rankings.

Responsibilities are intentionally separated:

- The engine is pure Dart. It accepts a board and a direction and returns a deterministic move result without accessing Flutter, storage, or Supabase.
- Tile models carry stable IDs so the UI can animate a tile from its old coordinate to its new coordinate.
- The provider owns runtime state, input locking, undo snapshots, milestone detection, animation phases, autosave coordination, and repository calls.
- Local storage serializes only the active run and local best score.
- The repository stores final runs, reads leaderboard data, resolves the current partner, and claims milestones.
- Widgets render provider state and do not implement merge rules.

## Gameplay Rules

- A new game starts with two random tiles in different empty cells.
- Each spawned tile is `2` with 90% probability and `4` with 10% probability.
- A valid swipe compresses all tiles, merges equal adjacent values once, and compresses the result again.
- A tile produced by a merge cannot merge again during the same swipe.
- The score increases by the value of every produced merge tile.
- A new tile spawns only when the board changed.
- An invalid swipe does not spawn a tile, change the score, create an undo snapshot, or consume an undo.
- Game over occurs only when the board has no empty cell and no horizontal or vertical merge remains.
- The first creation of a 2048 tile in a run triggers a celebration. The player can then continue indefinitely to 4096 and beyond.
- Milestones above 2048 use a compact notification rather than interrupting play with the full celebration overlay.

Canonical merge examples:

- `[2, 2, 2, 2]` becomes `[4, 4, 0, 0]`.
- `[2, 2, 4, 0]` becomes `[4, 4, 0, 0]`.
- `[4, 4, 8, 8]` becomes `[8, 16, 0, 0]`.
- `[2, 2, 4, 4]` must not become `[4, 8, 0, 0]` through a second merge in the same swipe.

## Move and Animation Model

Every tile has a stable ID, value, row, and column. A move result contains:

- the final board;
- the movement path for each source tile;
- merge groups and the resulting tile IDs;
- newly spawned tile metadata;
- score gained;
- highest tile;
- whether the board changed;
- whether the run reached a new milestone;
- whether no legal move remains.

The UI uses these events in phases:

1. Slide existing tiles to their destinations in approximately 140-180 ms.
2. Replace merged source tiles with the resulting tile and play a scale-pop for approximately 180 ms.
3. Spawn the new tile with a scale transition from zero to full size.
4. Animate the gained-score label upward while fading it out.

Swipe input is locked while these phases run. If the platform requests reduced motion, transitions become minimal or instantaneous while preserving state ordering.

## Undo

- Each run starts with three undo credits.
- Before every valid move, the provider stores one complete snapshot.
- Undo restores the board, score, highest tile, move count, elapsed duration, and milestone-celebration state from immediately before the move.
- Undo is unavailable when no valid move has been made, when no credits remain, while animation is active, or while a blocking overlay is open.
- Undo does not revoke an application milestone already confirmed by the server.
- Undo state and its remaining credits are included in local autosave.

## Scores and Application Points

The standard 2048 score and Kita Story application points are separate.

- Game score is the sum of all resulting merge values. It drives personal records and leaderboard ranking.
- Application points are awarded only when the authenticated user claims a tile milestone for the first time.

Milestone rewards:

| Tile | Application points |
|---:|---:|
| 128 | 2 |
| 256 | 3 |
| 512 | 5 |
| 1024 | 10 |
| 2048 | 20 |
| 4096 | 30 |
| 8192 and every doubled milestone above it | 50 |

If a player reaches several unclaimed milestones in one run, all newly crossed milestones are claimed. For example, a first run that reaches 2048 awards 40 total points. A milestone cannot be awarded twice, even after reinstall, restart, retry, or concurrent requests.

## Persistence

### Local active-run storage

The active run is saved after every completed valid move and after undo. The serialized snapshot contains:

- schema version;
- board values, stable tile IDs, and coordinates;
- current score and local best score;
- undo snapshots and credits remaining;
- move count;
- started-at timestamp and elapsed duration;
- whether the 2048 celebration has been shown;
- highest milestone reached in the run.

Corrupt or unsupported snapshots are discarded safely and presented as no active game. Closing with `Simpan & Keluar` retains the snapshot. Starting a replacement run requires confirmation and overwrites it. Game over or `Akhiri Permainan` removes the active snapshot after the final result has been queued for storage.

### Supabase results

`game_history` remains the shared result table. A migration adds nullable integer columns:

- `highest_tile`;
- `moves_count`.

A 2048 result uses:

- `game_type = '2048'`;
- `score` for the final standard game score;
- `highest_tile` for the maximum tile;
- `moves_count` for valid moves;
- `duration_seconds` for elapsed play time;
- `status = 'completed'` for game over or an explicitly ended run;
- `user_id` and `partner_id` for couple visibility through RLS.

Temporarily leaving a locally saved run does not create a result row.

### Milestone claims

A migration adds `game_achievements` with at least:

- `id`;
- `user_id`;
- `game_type`;
- `milestone`;
- `points_awarded`;
- `created_at`.

The database enforces uniqueness across `user_id`, `game_type`, and `milestone`. A database RPC claims a milestone and adds points atomically so repeated client requests are idempotent. Successful claims are also represented in `user_point_logs` using a specific activity type such as `2048_milestone_2048`.

## Leaderboard

The start screen loads completed 2048 results for the current user and linked partner.

- Ranking uses each person's highest score.
- A tie is broken by the higher tile, then fewer moves, then shorter duration, then earlier completion time.
- Ranking rows show avatar, name, score, highest tile, and completion date.
- A recent-history section lists the latest final runs for both people.
- The start-screen record card shows the highest visible couple score and opens the leaderboard bottom sheet when tapped.
- If there is no partner or the partner has no result, the leaderboard remains useful as a personal record view.

## Start Screen

The screen follows the visual structure established by Sudoku:

- use `lib/assets/game screen/Frame 1984078794 (1).png` as both the blurred hero artwork and game icon;
- show the `2048` title;
- show a milestone-reward badge such as `Hingga +120 poin`, representing milestones through 8192 while higher milestones remain available;
- show a tappable `Rekor Terbaik` card with the highest score;
- show `Mulai` when there is no active snapshot;
- show a primary `Lanjutkan` action and secondary `Mulai Baru` action when a snapshot exists;
- ask for confirmation before replacing an active run.

## Game Screen

The screen contains:

- a centered `2048` header and a back action;
- current score and best score;
- a responsive 4x4 board that does not rely on fixed phone dimensions;
- distinct pastel tile colors from 2 through 65536+, with a readable fallback style for larger values;
- swipe handling with a movement threshold and dominant-axis detection;
- an orange `Urungkan` button with the number of remaining credits;
- compact milestone feedback;
- 2048 celebration and game-over overlays.

The back button and Android system back share the same confirmation flow while a run is active:

- `Lanjut Bermain` closes the dialog;
- `Simpan & Keluar` saves locally and returns to the start screen;
- `Akhiri Permainan` records a final result, clears local state, and exits.

The 2048 celebration includes confetti, the score and achieved tile, and a `Lanjutkan Bermain` action. The game-over overlay includes final score, highest tile, new-record state, `Main Lagi`, and `Kembali`.

## Navigation Integration

The existing 2048 card in `games_screen.dart` will navigate to `Game2048StartScreen`. Other unfinished cards retain the current development bottom sheet behavior. Navigation uses the project's existing GoRouter conventions where practical; modal dialogs and bottom sheets continue to use Navigator APIs.

## Error Handling

- Gameplay never depends on network availability.
- Supabase failures do not discard a local run or block the game UI.
- Failed final-result writes are retained for retry rather than silently treated as saved.
- Failed milestone claims remain unconfirmed and can be retried safely because the database operation is idempotent.
- Invalid/corrupt local snapshots are removed and replaced with a clean start state.
- Input during animation or a blocking overlay is ignored.
- Repository failures produce concise user feedback and debug logging without exposing internal exception details.

## Testing Strategy

### Engine tests

- movement in all four directions;
- compression with and without gaps;
- canonical merge cases and one-merge-per-swipe behavior;
- score gain from one or multiple merges;
- no spawn after an invalid move;
- 90/10 spawn selection through injected deterministic randomness;
- winning milestone detection;
- legal-move and game-over detection.

### Provider tests

- initial two-tile setup;
- score, highest tile, and move count updates;
- animation input lock;
- exactly three undo operations;
- undo/autosave restoration;
- 2048 celebration shown only once per run;
- endless continuation;
- result finalization and local snapshot cleanup.

### Persistence and repository tests

- snapshot JSON round-trip and schema-version rejection;
- partner ID included in result payload;
- leaderboard sorting and tie breakers;
- milestone claim idempotency;
- retry state for failed writes.

### Widget tests

- start versus resume actions;
- responsive board on small viewports;
- swipe gesture integration;
- tile slide, spawn, and merge states;
- undo count presentation;
- exit confirmation from app-bar and system back;
- celebration and game-over overlays;
- leaderboard empty, personal-only, and couple states;
- no layout overflow.

Completion requires the full Flutter test suite to pass and `dart analyze lib/` to report no errors or warnings. Existing unrelated informational lints may be reported separately.

## Acceptance Criteria

- Standard 2048 movement and merge rules behave correctly for every direction.
- The player can reach 2048, see one celebration, and continue indefinitely.
- Tile movement, spawn, and merge are visibly animated without accepting overlapping input.
- Three undo credits work and survive app restart.
- Active games resume from local storage without network access.
- Final results appear in the current user/partner leaderboard.
- Application points are granted exactly once per milestone.
- Both navigation back paths protect an active run.
- The UI follows the supplied reference and existing Kita Story game styling.
- Automated tests cover engine edge cases, state transitions, persistence, and critical UI flows.
